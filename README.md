# 航班延误传播诊断与周转缓冲优化

这是一个面向数据分析岗位的 SQL、Power BI 与 Excel 作品集项目。项目使用美国交通部 BTS 航班准点数据，根据机尾号和时间顺序近似还原飞机轮转，分析前序延误如何传播到后续航段，并测算增加 5、10、15 分钟计划缓冲可能覆盖的延误起飞。

## 为什么做这个项目

常见作品集通常停留在销售额、RFM或简单航司排名。本项目选择一个需要还原业务过程的问题：单个航班的延误并不独立，同一架飞机会继续执行后续航段。分析重点因此从“谁延误最多”转为“延误在哪里传播、在哪里被吸收、运营计划可以优先调整哪里”。

## 交付内容

- `src/analyze.py`：兼容官方 BTS 字段及常见蛇形字段名的分析流水线。
- `sql/`：PostgreSQL 表结构、索引、轮转视图和 KPI 查询。
- `data/processed/`：实算 KPI、航线风险、缓冲情景和 Power BI 输入表（仓库收录关键汇总表，完整表可运行脚本重新生成）。
- `outputs/航空运营分析.xlsx`：运营总览、缓冲情景、高风险航线、指标字典（本地生成，二进制文件不入库）。
- `powerbi/`：页面设计、数据模型说明和 DAX 度量值。
- `docs/`：项目简报、业务假设和指标边界。
- `tests/`：时间转换和延误传播逻辑测试。

## 快速运行

```powershell
python src/analyze.py data/raw/bts_2024_01.zip --output-dir data/processed
python -m unittest discover -s tests -v
```

如果使用 BTS 官方月度压缩包：

```powershell
python src/download_bts.py --year 2024 --months 1
python src/analyze.py data/raw/bts_2024_01.zip --output-dir data/processed
```

扩展到完整年度时，把12个月文件一起传入 `src/analyze.py`。原始文件体积较大，默认不提交 GitHub。

## 核心方法

1. 将 HHMM 格式的计划及实际时间转换为时间戳，并处理跨午夜航班。
2. 按 `tail_number + scheduled_departure_ts` 排序，使用前序记录近似还原飞机轮转。
3. 仅保留机场衔接一致、前后航班正常完成且计划间隔在0至12小时的有效轮转对。
4. 前序到达延误不低于15分钟时，若后序起飞仍延误不低于15分钟，记为延误传播；否则记为延误吸收。
5. 根据延误率、严重延误率、取消率、P90延误和传播率形成航线风险排序。
6. 在静态假设下把计划起飞时间后移5/10/15分钟，估算可能从“延误”变为“准点”的航班数。

## 重要口径

- OTP15：正常完成且到达延误小于15分钟的航班占比。
- 航班完成率：未取消且未备降的航班占计划航班比例。
- 延误传播率：前序到达延误不低于15分钟的有效轮转中，后序起飞仍延误不低于15分钟的比例。
- 风险评分只用于样本内优先级排序，不是行业标准或因果模型。
- 缓冲模拟没有纳入飞机利用率、机组工时和机场时刻约束，因此不能表述为真实运营收益。

## 数据来源

- U.S. Department of Transportation, Bureau of Transportation Statistics, Reporting Carrier On-Time Performance.
- 官方入口：https://www.transtats.bts.gov/ONTIME/
- 当前实算数据：BTS 2024年1月 Reporting Carrier On-Time Performance，共547,271条计划航班记录。
- 原始月度压缩包约27MB，不放入GitHub项目包；可通过 `src/download_bts.py` 从官方入口重新下载。

## 隐私与数据说明

项目仅使用美国交通部 BTS 公开发布的数据，不包含任何个人身份信息。原始数据、简历相关临时文件与本地缓存均已排除在仓库之外。

当前交付物已使用完整月份刷新：识别461,224个有效轮转对，其中105,823个前序到达延误轮转用于传播分析。传播率为58.8%；在其他条件不变的静态假设下，增加5/10/15分钟计划缓冲可能覆盖14,682/26,383/35,802次延误起飞。上述结果只代表2024年1月，不能解释为因果效应或真实运营收益。
